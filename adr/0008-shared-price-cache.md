# 公開APIを継続利用し、共有キャッシュから価格を返す

- 日付: 2026-09-10
- 状態: 採用
- 関連: [ADR 0001](0001-tile-loading-and-cache.md)のブラウザ保存・再取得方針と、[ADR 0004](0004-cloudflare-deployment.md)のキャッシュ更新・D1移行の検討方針を一部置換

## 背景

過去年の探索や地点の推移表示では、同じ地域の複数年のデータを要求する。データは利用者によって変わらず、公示地価・基準地価は過去年になると更新頻度が低い。一律に短い期限で取得し直すと、別の利用者や再訪でも外部APIの応答待ちが発生する。

全国・過去年の一括取り込みとD1への保存も検討したが、初期取り込み、無料枠に合わせた分割、更新運用が必要になる。まず既存の公開APIと共有キャッシュを改善し、費用と運用の追加を抑える。

## 決定と理由

- 公開環境は既存のWorkers Cache APIを使う。元の取得URLに含まれる種別・年・タイルで区別し、利用者や取得優先度はキャッシュキーに含めない。APIキーは保存しない。
- 価格データがある過去年の公示地価・基準地価は長く再利用する。取得時の暦年と取引価格は短い期限とし、空の結果はさらに短くする。年越しで過去の取得結果の有効期間を後から延ばさない。新年度は別のキーになる。
- 鮮度の有効期間と、更新中に以前のデータを表示できる期間を分ける。空でない結果は期限後も限定期間だけ先に返し、低優先度で更新する。失敗時は元の取得日時を維持し、利用できる期間を延長しない。空の結果は期限後に取得完了を待ち、新規公開を発見する。
- Workerの背景更新は`waitUntil`で処理し、閲覧リクエストの切断に連動させない。更新の期限を設け、同一isolateではURLごとの時刻だけを共有して短時間の重複更新を抑える。PromiseやResponseをリクエスト間で共有しない。
- ブラウザには成功した新鮮なタイル応答だけを短くHTTPキャッシュさせる。先読み優先度はヘッダーに移し、通常表示とURLを揃える。期限切れデータ・エラー・一括範囲APIはHTTPキャッシュさせない。TanStack Queryのメモリキャッシュも継続する。
- ローカルNode.jsは同じ期限判定を使い、既存のメモリ・ディスク保存と同時取得の共有を維持する。共有キャッシュの検証は、別リクエストと別ブラウザコンテキストの両方で行う。

## トレードオフ

Cache APIはデータセンター単位の一時キャッシュであり、期限内の保持や全拠点の共有を保証しない。isolateをまたぐ重複取得も残る。初回の未取得年度は引き続き外部APIに問い合わせる。キャッシュへのヒットもWorkersへのリクエストとして数えられる。

古い年度への訂正は、次の更新またはキャッシュ失効まで反映が遅れる。背景更新の完了は次の取得から利用でき、開いている画面へのプッシュ通知や定期ポーリングは追加しない。ブラウザの保持期間を共有キャッシュより短くし、更新後の結果を取り直しやすくする。

## 見直す条件

キャッシュヒット率、未取得時の待ち時間、外部APIのアクセス制限、訂正の反映速度が問題になる場合は調整する。全拠点での取得統一や確実な永続保持が必要になった時点で、共通取得制御やDB保存を改めて検討する。
